# Passkeys

multipass holds passkeys in its store and signs you in with them on your Mac and iPhone, through a small app that each system lists as a passkey provider, with the store synced between them through iCloud Drive.

## 1. Problem

A passkey is a WebAuthn credential: a P-256 key pair that a site creates for you, where the site keeps the public key and you keep the private key. To sign in, the browser asks the operating system for a signature. The system hands the request to a passkey provider, such as iCloud Keychain or 1Password, which finds the matching private key and signs.

multipass cannot be that provider. It is a command-line tool, and macOS and iOS send passkey requests only to an AutoFill credential provider extension inside a signed app (`ASCredentialProviderViewController`, macOS 14 and iOS 17 and later). It also runs only on the Mac, so the store never reaches your iPhone. It also stores only text fields, with nowhere to keep a private key, a credential ID, and the site it belongs to. So every passkey you create today lives in iCloud Keychain or 1Password. Passkeys are replacing passwords on more sites each year, so a multipass that cannot hold them guards a shrinking share of your accounts.

## 2. Solution

A new app, `Multipass.app`, built for both iOS and macOS from one Xcode project, exists only to host a credential provider extension on each system. The extension links the existing Rust store code as a static library, so the store keeps one implementation. The store package moves into the app's iCloud Drive folder, so the iPhone, the Mac app, and the CLI share one package. It signs with Apple's CryptoKit, so multipass never implements elliptic-curve arithmetic itself. You unlock it with Face ID or Touch ID: the first sign-in on each device asks for the passphrase once, and the extension keeps it in that device's Keychain where only your face or fingerprint can read it. A passkey becomes a `passkey` field on an entry, beside the secret, username, notes, and one-time password, in store format 4. The CLI lists and removes passkeys. Only the extension creates them and signs with them, because only the extension receives the site's request.

This design depends on the answers to § 6. Until those are settled, this plan stays a draft.

### 2.1 How a sign-in works

1. A site calls `navigator.credentials.get()`. macOS or iOS shows its passkey sheet, which offers multipass among the providers.
2. You choose multipass. The system starts the extension and calls `prepareInterface(forPasskeyRegistration:)` for a new passkey, or its assertion counterpart for a sign-in.
3. The extension asks for Face ID or Touch ID and reads the passphrase from its Keychain item (§ 2.3). When there is no item, or the passphrase in it no longer opens the store, it shows its own passphrase field instead, and saves what you type to a new item. It then opens the store package through the Rust library, as the vault-key plan's § 2.3 describes: scrypt at work factor 18 on the key file, about 300 ms, then the store files under the vault key, merged.
4. For a sign-in, the extension finds the entry whose `passkey` matches the site's relying party ID and the requested credential ID, signs the authenticator data and client data hash with CryptoKit's `P256.Signing`, and returns an `ASPasskeyAssertionCredential`.
5. For a registration, the extension generates a key pair with CryptoKit and picks the entry for the site's relying party ID, such as `github.com`, by the first of these that applies:
   1. **The same account.** An entry whose passkey has the same relying party ID and user handle as the new one holds the same account registering again, so the new passkey replaces that one in place, as the WebAuthn specification has an authenticator replace an older credential for the same relying party ID and user handle.
   2. **An entry of the site's that the account can join.** The passkey joins an existing entry, beside its password and one-time password, when the entry holds no passkey, belongs to the site, and has no `username` or has the account's user name, compared ignoring ASCII case, since sites such as GitHub treat `Octocat` and `octocat` as one account. An entry belongs to the site when its name is the relying party ID or begins with it and a space, as `github.com octocat-work` does, or when one of its `website` lines matches `https://<rp id>` under the websites plan's `website::matches`, as an entry named `github work` with `website https://github.com` does. The match runs from the stored website to the relying party ID: a stored `https://github.com` matches the relying party ID `login.github.com`, but a stored `https://accounts.google.com` does not match `google.com`, so on google.com that entry does not belong to the site. The `website` rule applies once the websites plan has shipped, since that plan adds the field and the function; until then, an entry belongs to the site by name only. When several qualify, one whose `username` is the account's user name comes before one with none. Within each of those, the entry named exactly the relying party ID comes first, then entries whose name begins with it and a space, then entries matched only by `website`, and name order breaks any tie left, so `github.com` wins over `github work`.
   3. **A new entry.** Otherwise the extension creates an entry under the first of `<rp id>`, `<rp id> <user name>`, `<rp id> <user name> 2`, `<rp id> <user name> 3`, and so on, that no entry uses, with the account's user name as its `username`.

   It saves through the Rust library as a new store file in the package, as the vault-key plan's § 2.4 describes, and returns an `ASPasskeyRegistrationCredential` with "none" attestation.
6. The extension drops the decrypted store from memory and exits.

### 2.2 The `passkey` field

If the websites plan ships first, as its § 2.4 expects, it takes format 4 for its `website` field, and this field moves to format 5 on top of it. Format 4 adds one field to the mergeable-store plan's format 3, written on a single line as space-separated `key=value` pairs, each value base64 or escaped text:

```text
multipass 4
github.com
	modified 1764160000123
	username octocat
	passkey rp=github.com id=<base64 credential id> user=<base64 user handle> key=<base64 private key> created=2026-11-26
```

| Part | Meaning |
| --- | --- |
| `rp` | The relying party ID, the site's domain, which the system checks against the page |
| `id` | The credential ID that the extension generated at registration |
| `user` | The user handle that the site sent at registration |
| `key` | The 32-byte P-256 private key, as CryptoKit's raw representation |
| `created` | The registration date, for `list` |

An entry holds at most one `passkey` field, so each entry still describes one account. A second account on the same site that finds no entry of the site's to join gets its own entry, named `<rp id> <user name>`, such as `github.com octocat-work`, and the same account registering again replaces its passkey in place. A passkey never joins an entry whose `username` names another account; § 2.1 step 5 gives the order in which a registration picks its entry. Every entry holds at least one of `secret`, `otp`, and `passkey`.

The extension always reports a signature counter of 0, which the WebAuthn specification allows for keys that sync.

### 2.3 The Keychain item

The item holds the passphrase itself, not the vault key. The vault key rotates at least every 21 days and on every `passwd`, so an item holding it would go stale within weeks. A prompt in the extension may also have to rotate it, and rotating writes a new key file, which only the passphrase can encrypt.

| Attribute | Value | Why |
| --- | --- | --- |
| Class | Generic password, in a Keychain access group that the app and the extension share | The app's settings can remove it, and the extension reads it |
| Access control | `biometryCurrentSet` | Only a Face ID or Touch ID match reads it, and enrolling a new face or fingerprint makes it unreadable |
| Accessibility | `whenPasscodeSetThisDeviceOnly` | It never syncs to iCloud Keychain or leaves the device, and it disappears if the device's passcode is removed. Each device keeps its own item. |

After you change the passphrase with `multipass passwd`, the old item no longer opens the package's current key file. The next sign-in falls back to the passphrase field and replaces the item. Until iCloud delivers the deletion of the old key file, or for good if that `passwd` stopped before its last step, the package holds key files under both passphrases, and the item's passphrase still opens the older one. Whenever any key file in the package does not open with the item's passphrase, the extension neither signs nor saves until it has the passphrase that opens it. It asks for it in its own field. With both, it keeps the one whose key files carry the later `passphrase-set`, as the vault-key plan's § 2.3 step 3 does, saves that one to the item, and lets the vault-key code rotate under it. When you cancel the field, the sign-in or registration fails with `multipass needs your other passphrase`, and the next one asks again. The extension never signs read-only from the older lineage, because once the other Mac's rotation and compaction delete that lineage's store files, the older passphrase opens no store, and a sign-in that worked a moment ago would start failing for no visible reason. Refusing every time is simpler and never signs from stale data. The CLI never reads or writes the item; it asks for the passphrase, or, while a session is unlocked, for a touch, as the session-unlock plan describes.

### 2.4 Syncing through iCloud Drive

The store package lives at `Documents/store.multipass` in the app's iCloud container, which iCloud Drive copies between your devices. Its files are ciphertext, so iCloud holds nothing readable.

A store reaches the container through the app, the same way on every device. The first time you open the app, it runs an `NSMetadataQuery` over the container's `Documents` folder and waits for the query's first results, which list what iCloud Drive holds even before it downloads it. When the query finds `store.multipass`, the app uses it, and on a Mac it shows the `export MULTIPASS_STORE=…` line for the CLI. Only when the query finds none does the app offer to start: on a Mac, by moving an existing package in, and on any device, by creating a new store once you confirm that no other device of yours has one. The app never creates a store unasked. A device that creates `store.multipass` before iCloud Drive has delivered another device's makes iCloud Drive keep both and rename one with a number suffix (TN2336, § 7), and the renamed copy is a second store that the extension and the CLI never open.

TestFlight builds of a Mac app must be sandboxed, as the session-unlock plan's § 8.4 notes, so the app can neither see `~/.multipass` nor read `MULTIPASS_STORE`. To move a package, the app shows an open panel that starts in `~/.multipass` and asks you to choose the folder that holds the package. Choosing it grants the app access to that folder, through the `com.apple.security.files.user-selected.read-write` entitlement. When `MULTIPASS_STORE` names a package somewhere else, you choose that folder instead. The app refuses while the package still holds a move record from the vault-key plan's § 2.6, and says when the old single file beside it will be retired: at the first passphrase prompt 30 days after that file last changed. That old file is how an older multipass on another Mac still saves, and the move record's check finds it beside the package, so moving the package before then would lose those saves. Otherwise the app moves the whole `store.multipass` folder into the container with `FileManager.setUbiquitous(_:itemAt:destinationURL:)`, Apple's call for moving a local item into iCloud, which coordinates the move itself. It then shows the `export` line.

| Reader | How it reaches the store |
| --- | --- |
| The app and its extension, on both systems | Through the iCloud container, with `NSFileCoordinator` around listing the package, reading each file, writing each new one, and deleting each file a save, compaction, or rotation read |
| The CLI on the Mac | Through the container's path under `~/Library/Mobile Documents/`, which the CLI finds by itself when neither `--store` nor `MULTIPASS_STORE` is set and `~/.multipass` holds no store. When both hold one, the CLI refuses to choose (§ 6 question 10). The app's settings show the exact path and the `export` line, which is then optional. |

Every save adds a new file to the package and never modifies one, as the vault-key plan's § 2.4 describes, so iCloud never holds two versions of one file to reconcile. Opening merges what each device saved, entry by entry, as the mergeable-store plan describes. So the app and its extension need no conflict screen, and changes to different entries, made on two devices while one is offline, both survive. Changes to the same entry do not: the mergeable store keeps only the version with the newer `modified`. Because a new passkey's entry is named after the site's relying party ID and joins the site's existing entry (§ 6 question 7), two devices that register for the same site while one is offline write the same entry, and only the newer registration survives. A registration on the iPhone and a password edit to that entry on the Mac collide the same way. The other change is lost without a warning, and a lost passkey leaves the site holding a public key whose private key no device has. The mergeable store's password history (its § 2.6) keeps the losing version's secret and setup key as dated earlier values, so a lost password edit can be recovered with `get --previous`, but it keeps no passkey. Keeping a losing passkey the same way would be format 4's to design.

## 3. Why this design

- **A credential provider extension is the only way in.** Safari and the system passkey sheet send requests only to an extension that the app registers. A browser extension that overrides `navigator.credentials` works only inside that browser, and it moves the private key into the browser's process.
- **CryptoKit instead of hand-written P-256.** Constant-time elliptic-curve scalar multiplication is far harder to get right than the symmetric code in `src/crypto`, and a subtle mistake leaks the private key through timing or bad signatures. CryptoKit ships with macOS and iOS, as the Rust standard library ships with Rust. So the "no dependencies" rule treats Apple's system frameworks like the standard library: allowed, while third-party code stays banned.
- **Face ID and Touch ID from the start.** A passkey sign-in is meant to take a second, and typing a long passphrase each time defeats that, on a phone most of all. The cost is a second way into the store: anyone who passes Face ID or Touch ID on one of your devices can read the passphrase. `biometryCurrentSet` and `ThisDeviceOnly` limit that way in to your enrolled face or fingers on each device.
- **The Mac and iPhone together, through iCloud Drive.** A passkey that exists on only one device fails you on the other, so both ship at once. iCloud Drive is already on both devices and moves only ciphertext. A sync service of multipass's own would mean a server, which multipass refuses to run.
- **One store implementation.** Linking the Rust code means the extension reads and writes the store exactly as the CLI does. A Swift port would be a second implementation of scrypt, the age format, and the store text to keep in agreement.
- **The store stays symmetric.** Passkeys are public-key cryptography, and a large enough quantum computer could forge one from the public key that the site holds. That is true whichever provider keeps the private key. multipass still encrypts its store only with a passphrase, so holding passkeys adds no public-key step to the store itself.

Tests: format 4 round-trips through `to_text` and `from_text`, and literal format 2 and format 3 stores still open. The reader rejects an entry with two `passkey` lines, which catches a writer that stacks a second account's passkey onto the first entry, and an entry with none of `secret`, `otp`, and `passkey`, which catches a `passkey --clear` or any other write that leaves an entry empty. The entry choice in § 2.1 step 5 is tested over one store holding an entry named the relying party ID, one whose name begins with it and a space, and one matched only by `website`, each with and without a `username`; the test fails when a passkey joins an entry whose `username` names another account, or when the tie order changes. The C interface rejects a null or unterminated string. The extension's signature verifies under the public key it registered, checked with CryptoKit in a Swift unit test that runs on both platforms. The library's random bytes come from the system on iOS as well as macOS, checked by the same test that checks them on the Mac. Installing a build on a phone for these checks waits for the user to ask.

## 5. Cost

Each sign-in opens the store package once after the Face ID or Touch ID prompt. That takes about 300 ms at work factor 18 on an Apple-silicon Mac; scrypt's 256 MiB of memory is the cost to measure on the iPhone, inside an extension's memory limit, in the prototype. One P-256 signature is too small to notice. iCloud Drive usually syncs within seconds to minutes, so a passkey registered on one device may not be on the other right away. The two app builds and the XCFramework add several minutes to CI on each push.

## 6. Open questions

Question 5 blocks the plan until the prototype in § 8 answers it. Questions 1 to 4 and 6 to 10 are decided.

1. **Apple frameworks and "no dependencies".** Decided: sign with CryptoKit. Apple's system frameworks count like the Rust standard library, and third-party code stays banned.
2. **Platforms.** Decided: the Mac and iPhone together, with the store synced through iCloud Drive as § 2.4 describes.
3. **Distribution.** Decided: TestFlight on both the Mac and the iPhone, under one App Store Connect record, so every device updates the same way. The App Store can follow later, if the app is opened to others.
4. **Unlocking in the extension.** Decided: Touch ID from the start, with the passphrase kept in the Keychain as § 2.3 describes.
5. **Reaching the iCloud container from the extension.** § 2.4 has the extension read the store from the app's iCloud container. Whether an AutoFill extension may open that container directly, or needs the app to keep a copy in a shared App Group container, is unverified. Owner: the implementer, through a prototype, before this plan goes `ready`.
6. **How one project builds both apps.** Decided: a SwiftUI multiplatform app. If the prototype shows that Mac Catalyst would share more of the extension's code, the implementer switches to Catalyst and records why here. The unmodified iPad build on the Mac ("Designed for iPad") is ruled out, because it runs only on Apple-silicon Macs and may not run the extension.
7. **Naming a new passkey's entry.** When a site registers a passkey, the extension must choose an entry. Decided: use the site's relying party ID, such as `github.com`, as the name, and add the `passkey` field to an existing entry of the site's, grouped with its password and one-time password as `otp` is. § 2.1 step 5 gives the rule for which entry: an entry also belongs to the site when one of its `website` lines matches the relying party ID, whatever its name, a passkey joins an entry only when the entry's `username` is empty or the account's user name, and the entry named exactly the relying party ID wins a tie.
8. **One passkey per entry, or several.** A second account on the same site registers a second passkey for the same relying party ID. Decided: one passkey per entry, with the second account's entry named `<rp id> <user name>`, such as `github.com octocat-work`, so each entry still describes one account. Every other account on the site that finds no entry of the site's to join gets `<rp id> <user name>` under its own user name too. Only when an entry of that name exists that the account cannot join does it take the first unused name of `<rp id> <user name> 2`, `<rp id> <user name> 3`, and so on. The same account registering again, matched by its relying party ID and user handle, replaces its passkey in place, as § 2.1 step 5 describes.
9. **Removing a passkey without its entry.** `rm` deletes a whole entry, including its password. Decided: `multipass passkey <name> --clear`, which mirrors `otp --clear`. An entry must then hold at least one of `secret`, `otp`, and `passkey`, so `--clear` fails when it would leave the entry empty.
10. **The CLI on a Mac whose store moved.** Once the app moves the package into its container (§ 2.4), `~/.multipass` holds no store: the app moves only after the old `store.age` is retired. With `MULTIPASS_STORE` unset, the CLI would find nothing, and `multipass init` would create a second, empty store that no other device sees. Decided: when neither `--store` nor `MULTIPASS_STORE` is set and `~/.multipass` holds neither `store.multipass` nor `store.age`, the CLI uses the container's package when it exists. `init` resolves the same default, so it finds that package and refuses, as it refuses for any store that exists, and the `export` line becomes optional. Nothing pins the CLI to the container, though, so a store can appear in `~/.multipass` afterwards: from `init` on a second Mac before iCloud Drive lists the package there, or from an older multipass's `init`, whose `store.age` the vault-key plan's § 2.6 would move into a local package. So when neither is set and both `~/.multipass` and the container hold a store, every command fails before § 2.6 moves anything, naming both paths and the `export` line that picks each, rather than quietly saving where no other device reads. When `--store` or `MULTIPASS_STORE` still names the package's old path after the move, the CLI finds no store there, and its error names the container's package and the `export` line. `init` with that path creates the store you named, since you named it, but first notes on stderr that the container holds one. Rejected: keeping `~/.multipass` as the CLI's only default, with the `export` line as the one way to reach the container and `init` only warning when the container holds a store.

## 7. Background

- Apple opened passkey providers to third-party apps in iOS 17 and macOS 14 (Sonoma), with new methods on `ASCredentialProviderViewController` (Matt Miller, "WWDC23 passkeys", blog.millerti.me, 2023-06-10).
- The Rust standard library supports `aarch64-apple-ios` and `aarch64-apple-ios-sim` as well as the Mac targets, so the same zero-dependency code builds for the iPhone.
- Not yet verified, so the prototype checks it: whether Chrome on macOS offers third-party providers. Safari does. One developer reports that macOS shows third-party providers to sites as "iCloud Keychain" by zeroing the AAGUID.
- The FIDO Alliance's Credential Exchange Format, v1.0 with errata dated 2026-03-09, and its Credential Exchange Protocol define how to move passkeys between providers. 1Password helped write them. Importing your existing passkeys from 1Password would use them, and that belongs in a later project.
- Apple's "Designing for Documents in iCloud", section "Design for Network Transfer Efficiency" (https://developer.apple.com/library/archive/documentation/General/Conceptual/iCloudDesignGuide/Chapters/DesigningForDocumentsIniCloud.html), says a file package's elements "can be read and written separately", and "only changed elements are uploaded or downloaded". So per-file transfer inside a package is documented.
- Neither that guide nor TN2336, "Handling version conflicts in the iCloud environment" (https://developer.apple.com/library/content/technotes/tn2336/_index.html), says whether a conflict inside a package is reported for the package or for each file, or what happens when two devices add different files to one package and delete the same one. TN2336 says data-scope conflicts resolve "by picking up a winning version and keeping the other changes in a losing version", without saying at which level. It also says that in the Documents folder a new-file conflict, two devices creating a file of the same name, produces a "bounced" copy, which the vault-key plan's random file names avoid. Both pages are in Apple's documentation archive. So per-file conflict behavior is undocumented, and the prototype's two-device test in § 8 step 1 settles it, with not declaring the package type as the fallback.

## 8. Rollout

These steps run in order. Steps 2 and 4 need the user's Apple developer account and devices.

1. **Prototype.** Build a bare extension that registers and signs with a fixed test key on both platforms, and answer question 5: can the extension open the app's iCloud container directly? Also measure scrypt at work factor 18 inside the iPhone extension's memory limit, and check whether Chrome on the Mac offers the extension. Confirm, too, that iCloud Drive syncs the files inside a declared package one by one, as expected. Apple documents per-file transfer for packages, but not how conflicts inside one are reported (§ 7), and other apps that keep packages in iCloud Drive rely on per-file sync, as the vault-key design does. The test: with the app installed and `.multipass` declared as a package type, two devices each save to the same package while one is offline, the way the vault-key plan's § 2.4 saves: each adds a different new file and deletes the one store file both read. Both new files survive, the file both read is gone, and no `NSFileVersion` conflict version appears for the package. If a conflict version does appear, the app does not declare the package type, which leaves a plain folder that syncs per file, as today. Check, too, that the CLI finds the container's package when iCloud Drive lists it but has not downloaded it, or has evicted it to save space, and that opening it downloads the files rather than failing or treating the store as missing. Record the results in § 7, and move this plan to `ready`.

4. **TestFlight.** Upload builds for both platforms. The user installs them from TestFlight on the Mac and the iPhone, and runs the checks in § 4's table.
